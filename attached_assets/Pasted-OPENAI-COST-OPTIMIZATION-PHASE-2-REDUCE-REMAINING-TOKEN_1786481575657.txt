OPENAI COST OPTIMIZATION PHASE 2 — REDUCE REMAINING TOKEN DUPLICATION

The previous optimization work is largely correct.

DO NOT redesign the architecture.
DO NOT remove dependency fingerprinting.
DO NOT remove OpenAI usage tracking.
DO NOT change investment logic unless explicitly described below.

I have reviewed the implementation and there are still several significant token-cost opportunities.

The purpose of this task is to reduce INPUT TOKENS and WEB SEARCH COST while preserving analytical quality.

==================================================
1. FIX callAiWithWebSearch — SEARCH CONTEXT MUST NOT ALWAYS BE HIGH
==================================================

Currently ai-service.ts hardcodes:

tools: [{ type: "web_search", search_context_size: "high" }]
tool_choice: "required"

This means every call using callAiWithWebSearch performs a HIGH-context web search.

Change AiServiceOptions to support:

webSearchContextSize:
"low" | "medium" | "high"

and:

webSearchRequired:
boolean

Use sensible defaults.

Do NOT hardcode "high" globally.

Recommended initial configuration:

Market Monitor:
medium

News Monitor:
medium

Event Monitor:
low or medium

Sector Monitor:
medium

Investor Watch discovery:
low

Investor Watch full material analysis:
medium

Company Monitor:
medium

Opportunity Finder:
medium

HIGH should only be used when a module explicitly needs unusually broad/deep research.

Keep this configurable centrally.

==================================================
2. IMPLEMENT A REAL DOWNSTREAM AI CONTEXT LAYER
==================================================

The current implementation manually creates smaller JSON objects inside several downstream modules.

This is better than sending full results, but it still causes duplicated and inconsistent context construction.

Create a deterministic backend context layer.

Example location:

src/lib/downstream-ai-context.ts

It must NOT call OpenAI.

It should expose functions such as:

getMarketAiContext()
getNewsAiContext()
getEventAiContext()
getSectorAiContext()
getCompanyAiContext(symbol)
getPortfolioAnalyzerAiContext()
getRiskAnalyzerAiContext()
getOpportunityAiContext()
getMarketAlertsAiContext()

These functions must return small structured objects specifically intended for machine-to-machine AI reasoning.

The existing full repository results remain unchanged.

==================================================

Do not simply copy most fields from the original result.

For example, Market Monitor downstream context should resemble:

{
  sentiment,
  riskLevel,
  materialDrivers,
  keyRisks,
  materialVersion
}

NOT:

summary
executiveSummary
positiveFactors
negativeFactors
strongSectors
weakSectors
keyRisks
long descriptions
etc.

News context should contain only MATERIAL current developments.

Example:

{
  materialNews: [
    {
      id,
      category,
      importance,
      affectedSymbols,
      impact
    }
  ],
  materialVersion
}

Do not send long article summaries unless required.

Event context:

{
  upcomingMaterialEvents: [
    {
      id,
      date,
      importance,
      affectedSymbolsOrMarkets,
      impactType
    }
  ]
}

Example:

{

  thesisChanges,
  topRisks,
  topCatalysts,
  nextEvent,

}

Do NOT send full:

executiveSummary

businessDescription
bullCase

bearCase

sectorContext prose
all thesis prose

to every downstream module.

Those remain available in the full Company Monitor result/UI.

4. TRADE DECISION NEEDS PARTICULAR ATTENTION
==================================================

Trade Decision currently receives context from many modules.

Reduce this aggressively but safely.

Trade Decision should primarily receive:

portfolio state
Portfolio Analyzer compact context
Risk Analyzer compact context
Market Alerts compact context
Opportunity Finder compact candidates
relevant Company compact contexts
relevant blockers/events
relevant Price Context
previous active decisions

Do NOT send Market Monitor, News Monitor and Sector Monitor separately when their material implications are already represented by Portfolio Analyzer, Risk Analyzer, Alerts or Company Monitor.

Only include raw upstream monitor context when it contains a MATERIAL item that is not represented by those higher-level analyses.

Avoid information fan-out where the same market fact reaches Trade Decision through 3-5 different module outputs.

7. PRICE CONTEXT
==================================================

Price Context is deterministic backend data.

Keep it.

But reduce its textual representation.

Do not repeatedly send explanatory prose such as:

"StabilizingAfterDecline does NOT confirm a bottom..."
"PossibleRecovery does NOT confirm..."
etc.

These rules belong in the SYSTEM PROMPT once.

Price data sent in the user prompt should be compact structured data.

Example:

SERV:
{
  state:"StrongDowntrend",
  recent:"Stabilizing",
  r5d:-10.27,
  r1m:-15.64,
  r3m:-39.93,
  volatility:"High"
}

Do not send verbose explanations for every ticker.

==================================================
8. REMOVE JSON PRETTY PRINTING FROM AI PROMPTS
==================================================

When JSON is sent to OpenAI, do not use:

JSON.stringify(data, null, 2)

unless humans need to read that exact prompt.

Use:

JSON.stringify(data)

for production AI requests.

Pretty printing adds unnecessary whitespace tokens.

Debug UI may pretty-print the stored request separately for human readability.

This is a small optimization but essentially free.

10. COMPANY MONITOR NO-CHANGE PATH
==================================================

Company Monitor remains potentially expensive because every qualifying refresh performs a full web-search analysis.

Add an optional lightweight discovery stage similar to Investor Watch.

For an existing company analysis:

Stage 1:
cheap targeted web-search discovery using a small model and LOW search context.

Question only:

"Are there new MATERIAL company-specific developments since lastMaterialUpdateAt?"

Look for:
earnings
guidance
regulatory decisions
material analyst revisions
major contracts
capital raises
material corporate announcements
other thesis-changing developments

Return only:

{
  materialDevelopmentFound: boolean,
  categories: [],
  shortReason: ""
}

Maximum output approximately 100-150 tokens.

If FALSE and Price Context has not materially changed:

DO NOT run full Company Monitor analysis.

Preserve existing analysis.
Update lastCheckedAt.
Record NoMaterialChange.

If TRUE:

run full Company Monitor analysis.

IMPORTANT:
Price Context changes may independently require re-evaluation according to existing material price-state thresholds.

Do not use the discovery stage to ignore meaningful price-state changes.
