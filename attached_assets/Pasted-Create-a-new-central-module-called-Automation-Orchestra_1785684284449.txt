Create a new central module called:

Automation Orchestrator

This module is the central scheduler, dependency manager and operational status dashboard for the entire application.

Individual modules must not each own independent timers.

The Automation Orchestrator must centrally decide:

* which modules should update
* when they should update
* in which order they should update
* why they were triggered
* whether the update succeeded
* whether dependent modules must run afterwards

The Orchestrator must not contain investment logic.

It must only coordinate the existing modules.

⸻

CORE RESPONSIBILITY

The Orchestrator should answer:

“What should be updated now, and what should run afterwards?”

It should support:

* manual updates
* scheduled updates
* dependency-based updates
* event-triggered updates
* stale-data detection
* retry handling
* pause/resume
* operational status monitoring

The purpose is to ensure the application remains current without requiring the user to manually visit and update every module.

⸻

AUTOMATION MODES

Add three system-wide automation modes:

Manual

SemiAutomatic

FullAutomatic

Manual:

* No module runs automatically.
* The user starts updates manually.
* The Orchestrator still shows module status, dependencies and stale data.
* “Run all now” and individual “Run now” actions remain available.

SemiAutomatic:

* Monitoring and analysis modules run automatically.
* Trade Decision and Trade Review may also update automatically.
* No trade is approved or executed automatically.
* Trade Review still requires manual approval.

FullAutomatic:

* Reserved for a later version.
* The complete analysis and decision flow may run automatically.
* Future policy checks may allow ready trade proposals to proceed without manual approval.
* Do not implement automatic approval or execution now.
* Show FullAutomatic as disabled or “Coming later” until policy and execution modules exist.

Store the selected mode centrally.

The mode must survive application restarts.

DEPENDENCY FLOW

The Orchestrator must understand module dependencies.

Do not run downstream modules before required upstream modules are sufficiently fresh.

Recommended base dependency graph:

Portfolio Manager:

* independent external data source

Market Monitor:

* independent analysis source

News Monitor:

* independent analysis source

Event Monitor:

* independent analysis source

Sector Monitor:

* depends on sufficiently fresh Market Monitor and News Monitor when available

Company Monitor:

* runs for selected companies when triggered by relevant events, news or portfolio exposure

Market Alerts:

* depends on fresh portfolio and recent monitor data

Risk Analyzer:

* depends on Portfolio Manager, Market Alerts, relevant Company Monitor data, Market Monitor and Event Monitor

Portfolio Analyzer:

* depends on Portfolio Manager, Risk Analyzer, Market Monitor, Sector Monitor and relevant Company Monitor data

Opportunity Finder:

* depends on Portfolio Manager, Portfolio Analyzer, Sector Monitor, Market Monitor, Event Monitor and News Monitor

Trade Decision Engine:

* depends on Portfolio Manager, Risk Analyzer, Portfolio Analyzer, Market Alerts, Opportunity Finder and relevant Company Monitor data

Trade Review:

* runs immediately after a successful Trade Decision update
* does not call OpenAI
* rebuilds ready and waiting presentation from the latest Trade Decision result

Avoid dependency cycles.

The Orchestrator should reject invalid registry configurations that create cycles.

EVENT-DRIVEN CHAINS

Support event-triggered update chains.

Example: important news about a held company

News Monitor detects an important development
→ Company Monitor for affected ticker
→ Market Alerts
→ Risk Analyzer
→ Portfolio Analyzer
→ Trade Decision Engine
→ Trade Review

Example: blocking earnings event has passed

Event Monitor detects the event has passed
→ Company Monitor for affected ticker
→ Market Alerts
→ Risk Analyzer
→ Portfolio Analyzer
→ Trade Decision Engine
→ Trade Review

Example: portfolio changed

Portfolio Manager detects changed positions or cash
→ Risk Analyzer
→ Portfolio Analyzer
→ Opportunity Finder when materially relevant
→ Trade Decision Engine
→ Trade Review

Only trigger downstream modules when the upstream result indicates a meaningful change.

Do not rerun the full chain after every harmless refresh.

⸻

MEANINGFUL CHANGE

Each module runner should report whether a meaningful change occurred.

Suggested values:

* None
* Low
* Medium
* High

The Orchestrator should use this to decide whether downstream modules need to run.

Examples:

* timestamp-only refresh: None
* small wording change: Low
* new important company alert: High
* portfolio position changed: High
* risk score changed materially: Medium or High
* Trade Decision readiness changed: High

Do not let OpenAI decide scheduling directly.

Scheduling decisions should be deterministic backend logic based on module results and configured rules.

⸻

STALE-DATA HANDLING

The Orchestrator should calculate whether each module is:

* Fresh
* DueSoon
* Stale
* Running
* Failed
* Disabled
* WaitingForDependency

If a required dependency is stale:

* update the dependency first
* do not run the downstream module with knowingly stale critical input unless explicitly allowed
* show why the downstream module is waiting

Example:

Trade Decision:
Waiting for fresh Risk Analyzer

RETRIES AND FAILURE ISOLATION

Use bounded retries.

Reuse the existing module-level retry and OpenAI timeout behaviour.

The Orchestrator should not retry indefinitely.

If one module fails:

* record the failure
* keep previous successful module data
* do not incorrectly mark downstream modules as updated
* block only downstream jobs that require the failed result
* allow unrelated modules to continue

Show the latest useful error in the GUI.

⸻

PROCESS LIFECYCLE

The schedule must run on the backend, not in the browser.

Closing the browser must not stop the schedule while the backend deployment is running.

On backend startup:

* restore persisted schedules
* detect abandoned Running jobs
* mark abandoned jobs failed or retryable
* recalculate nextRunAt
* avoid replaying every missed interval
* run one recovery check when appropriate

Do not create frontend timers that invoke backend modules directly.

The frontend only displays state and sends explicit user commands.

⸻

IMPORTANT ARCHITECTURE RULES

The Orchestrator must not:

* duplicate module analysis logic
* modify module results itself
* make investment decisions
* approve trades
* execute trades
* directly write fake analysis results
* rely on the browser remaining open
* create separate uncontrolled timers inside modules

Each module remains responsible for producing its own result.

The Orchestrator is responsible only for:

* scheduling
* sequencing
* dependencies
* triggering
* operational state
* retry coordination
* visibility

The final flow should be:

Automation Orchestrator
→ updates monitoring and analysis modules
→ Trade Decision Engine re-evaluates decisions
→ waiting ideas remain waiting or become ReadyForReview
→ Trade Review synchronizes
→ user manually approves ready trades

Full automatic trade approval and execution will be added later as a separate safety and execution phase.
