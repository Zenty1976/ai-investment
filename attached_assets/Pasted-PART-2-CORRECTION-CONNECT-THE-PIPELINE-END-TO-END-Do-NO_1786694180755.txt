PART 2 CORRECTION — CONNECT THE PIPELINE END-TO-END

Do NOT redesign Catalyst Intelligence.

Most of the Part 2 components are good and should be preserved.

However, inspection of the implementation shows that several new components are
not actually connected to the production Catalyst pipeline.

Fix the following issues.


==================================================
1. CRITICAL — CATALYST SCREENING DOES NOT USE THE NEW UNIVERSE
==================================================

catalyst-universe.ts correctly contains collectAllScreenableTickers(), including
the proactive universe.

However routes/catalyst-intelligence.ts still contains its own old
collectScreenableTickers() implementation which only collects:

- Portfolio Manager
- Opportunity Finder
- Company Monitor

This defeats the main purpose of Part 2.

REMOVE this duplicated old discovery logic.

Use the canonical catalyst-universe abstraction.

POST /api/catalyst-intelligence/screen must be capable of screening candidates
that are NOT already:

- portfolio holdings
- Opportunity Finder candidates
- Company Monitor entries.

There must be ONE canonical implementation for the screenable universe.


==================================================
2. DO NOT RELY ON A SMALL HARDCODED STOCK LIST AS THE REAL UNIVERSE
==================================================

catalyst-universe.ts currently contains DANISH_SEED and US_SEED hardcoded ticker
lists.

A small static seed can remain as fallback/test/bootstrap data if useful.

It must NOT be the production definition of:

"supported Danish and US equities".

Inspect the existing Saxo instrument/security-search capabilities.

Build the production universe from actual supported/tradeable Saxo instruments
where possible.

Store/cache the resulting universe so this does NOT repeatedly call Saxo.

The universe should contain compact metadata:

ticker
company
exchange
country
currency
sector/industry where available
UIC/instrument identifier
tradeable
active

If Saxo cannot provide the complete universe through the currently implemented
API, report exactly what is missing instead of pretending the static seed is the
complete market universe.

==================================================

Part 2 created:

catalyst-company-events.ts

Investor Day

Fix this.

For each ticker:

look for upcoming CompanySpecificEvents

and build CatalystFacts from the actual event.

EARNINGS is one ScheduledCatalystType.

It must NOT be the only real production path.


==================================================
4. CONNECT COMPANY EVENT DISCOVERY TO AUTOMATION
==================================================

Currently:

POST /api/company-events/discover/:ticker

can discover scheduled events via web search.

But this appears to be primarily a manually callable endpoint.

That is insufficient.

The system must proactively discover upcoming events.

Design a COST-SAFE orchestrator-controlled discovery process.

IMPORTANT:

Do NOT web-search every stock on every Run All.

Use:

cached event state
last discovery timestamp
event fingerprints
minimum refresh windows
existing Event Monitor information
official/structured sources where available

Only perform web discovery when due.

The orchestrator should progressively maintain upcoming company catalysts.

The result must be:

A company can enter Catalyst Intelligence because the system discovered a
scheduled event — without the user manually opening that company first.


==================================================
5. SPACE-X-STYLE FLOW MUST WORK END-TO-END
==================================================

The following generic scenario must work:

Company X is NOT:

- in portfolio
- in Opportunity Finder
- in Company Monitor.

There is a publicly known company meeting/product/technology event in 5 days.

The system discovers the event.

↓

Company X becomes a Catalyst candidate.

↓

Pre-event screening occurs.

↓

If sufficiently important, Company Driver Profile is generated/reused.

↓

Expectations/reporting/rumors are investigated.

↓

Price Context is evaluated.

↓

Catalyst Intelligence can produce:

MONITOR
INVESTIGATE
HIGH_INTEREST

↓

If qualified, Company X can be promoted to Opportunity Finder.

NO manual addition of Company X should be required.

==================================================

Current analyze/:ticker logic can stop with:

"No upcoming event found — no facts to analyze"

Refactor CatalystFacts / screening so a valid CatalystFacts object can exist for:

triggerType = EMERGING_SETUP

rather than requiring a fake earnings event.

Then:

signals
company state
price context
sector
market
news

can create an Emerging Setup.

Do NOT require earnings or any scheduled event for PATH B.


==================================================
7. CONNECT DRIVER-DIRECTED RESEARCH TO STORED SIGNALS
==================================================

catalyst-driver-profile.ts contains buildDriverSearchTopics().

Good.

But deep Catalyst analysis currently mainly injects the driver profile into the
AI call and lets web search happen inside that analysis.

That is not enough for stateful Signal Accumulation.

Implement the intended flow:

CompanyDriverProfile

→ determine current driver information already available from
  News Monitor / Event Monitor / Sector Monitor / Market Monitor

→ identify missing/material driver indicators

→ targeted research only where warranted

→ normalize findings into LeadingIndicatorSignal records

→ store signals with:
   signalId
   ticker
   driver
   direction
   observationDate
   publishedAt where available
   source
   sourceType
   sourceOriginId
   canonicalSource
   sourceQuality
   freshness
   causal relevance
   fact/interpretation classification

→ feed STORED signals into SignalAccumulationState

→ then run deep Catalyst analysis.

This is necessary so 7D/14D/30D signal accumulation represents actual historical
evidence rather than only the signals present in one AI request.
