FIX BROKEN RECENT-RUN / REPEATED RUN-ALL AI PROTECTION

We have now measured real OpenAI usage by running:

Run All
→ wait only a few minutes
→ Run All again

The second Run All still caused approximately:

+19 API calls
+104.6k tokens
+$0.243 estimated cost

This is far too much when the system was fully updated only minutes earlier.

IMPORTANT:
Do NOT solve this by simply adding arbitrary cooldowns everywhere.

I inspected the current architecture and there appears to be a concrete bug in how the existing recent-run guard records the last actual AI execution.

CURRENT PROBLEM

automation-orchestrator.ts already contains:

OBSERVATION_MODULE_MIN_REFRESH_MINUTES

including approximately:

market-monitor = 15 min
news-monitor = 15 min
event-monitor = 60 min
sector-monitor = 180 min
opportunity-finder = 180 min

The recent-run guard checks:

entry.lastAIAnalysisAt

This is correct in principle.

However, after a successful orchestrator execution, lastAIAnalysisAt is currently updated through:

analysisRepository.setFingerprint(...)

and setFingerprint() is only called when:

pendingFingerprint = computeFingerprint(...)

returns a value.

This creates a bug.

Modules such as:

market-monitor
news-monitor
opportunity-finder

do not have STATIC_DEPS fingerprint definitions.

computeFingerprint() therefore returns null.

Because pendingFingerprint is null:

setFingerprint() is not called

and therefore lastAIAnalysisAt is not updated.

The recent-run guard consequently has no reliable timestamp proving that OpenAI just ran.

This allows a second Run All only minutes later to call OpenAI again.

Opportunity Finder is particularly expensive:
our measured second Run All increased Opportunity Finder from approximately:

52.1k total tokens
to
103.8k total tokens

with only one additional Opportunity Finder call.

That one repeated analysis therefore consumed roughly 51.7k tokens.

GOAL

Separate these two concepts:

1. dependencyFingerprint
2. lastAIAnalysisAt

lastAIAnalysisAt must NOT depend on whether a module supports dependency fingerprinting.

Every successful execution that ACTUALLY called AI must record lastAIAnalysisAt.

A module may have:

lastAIAnalysisAt = timestamp
dependencyFingerprint = undefined

That is perfectly valid.

IMPLEMENTATION

Modify AnalysisRepository so lastAIAnalysisAt can be updated independently from dependencyFingerprint.

For example add a method conceptually similar to:

markAIAnalysis(moduleName, timestamp)

Do not require a fingerprint argument.

After every successful orchestrator-controlled AI execution:

- always update lastAIAnalysisAt
- only update dependencyFingerprint if computeFingerprint() returned a fingerprint

Conceptually:

if actual AI was called:
    markAIAnalysis(repoKey, aiCallAt)

if pendingFingerprint exists:
    set dependencyFingerprint

Do NOT falsely update lastAIAnalysisAt when an AI call was skipped.

SKIPPED_RECENT:
- preserve previous lastAIAnalysisAt

SKIPPED_UNCHANGED:
- preserve previous lastAIAnalysisAt

The timestamp must mean:

"the last time this module actually spent an AI call"

not:

"the last time the module was checked."

Inspect modules such as:

Sector Monitor

Do not mark a full AI analysis as executed when the route returned without the relevant AI call.

The orchestrator must only advance lastAIAnalysisAt for the AI execution being protected when AI was genuinely called.

For Company Monitor, preserve the distinction between:

If separate timestamps are required, use explicit names such as:

lastDiscoveryAt

rather than mixing their meanings.
